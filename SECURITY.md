# Security

## Reporting a vulnerability

Please report security issues privately through
[GitHub's private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing-information-about-vulnerabilities/privately-reporting-a-security-vulnerability)
on this repository, not in a public issue. Expect an acknowledgement within a week.

## Threat model and known limits

Carousel is a device for a home network. What it does and does not protect:

| Area | Behaviour |
| --- | --- |
| Web pages (Stage, Running order, Images, Panel, Wi-Fi) | Sign-in with a 6-digit code the panel shows while someone asks (2 min validity, 5 attempts, then 30 s before a new code). The browser then keeps a cookie holding a 128-bit device secret (`HttpOnly`, `SameSite=Strict`, which also stops cross-site form posts). "Sign out every other browser" makes a new secret; a factory reset too. Requests whose `Host` is not the panel's IP, its access point IP, `carousel.local` or its own `carousel-xxxx.local` are refused (DNS rebinding), and so are browser requests coming from another site (`Origin`, `Sec-Fetch-Site`), so a web page cannot burn sign-in attempts or pop codes up. Known limit: a device on the same network can still post wrong codes and keep sign-in locked, 30 s at a time. Every page and browser route checks the host, a cross-site origin and the session cookie before anything else, then the lock (the locked page, status 503); no `GET` changes a stored setting, and every value a page shows that the firmware did not write itself (network names, session names, image names, the host, the message, update text) is escaped. The home page's picture of the panel (`/preview`) needs the same cookie: without it, it answers 401 and never opens sign-in (which would put a code on the panel); it is black while a sign-in code is on the panel, so no page ever carries the code, and it is never cached. The image files (`/images/f`) are read-only too: 401 without the cookie (never the sign-in page), only for a name the panel stores exactly, as `image/gif` with `nosniff` and a `sandbox` policy. Only the stylesheet and the poster sheet (`/s/<version>/c.css`, `/s/<version>/p.png`) are public: they are part of the firmware and carry no data. The browser routes of the Stage page and the Wi-Fi form (`POST /show`, `/brightness`, `/text`, `/wifi`) check, in this order and before one byte of the body is read: the host and a cross-site origin (403), the session cookie, never the API token (else the sign-in page), the announced size, at most 512 bytes (a negative one: 400; over 512: 413), then the lock (the locked page); the body is then read into a 512-byte buffer on the heap, freed once answered, with 1 s allowed between bytes. A multipart body is read by the web server library before these checks, then refused (415). Plain HTTP: the cookie can be read by anyone sniffing the network; do not expose the panel to the internet. |
| Coding agent endpoint (`/agent/<state>`, and `/claude/<state>`), `/install` and `/id` | A hook call carries the hook token in the `X-Hook-Token` header: a 128-bit secret of its own, created at the first start, separate from the session secret and the API token, compared in constant time, and accepted for nothing else (the API token and the cookie are not accepted as a hook token). Without it, or with an old one, the panel answers 401 before reading any body byte, posts no event and writes nothing; the refusals are counted in RAM and logged by kind at most every 10 s, and the Panel page says how many. A browser request from another site is refused first (403). Renew on the Panel page and a factory reset replace the token; "Sign out every other browser" keeps it. The setting "Accept hooks without a token" (Advanced, off by default) restores the open behaviour: then anyone on the network can post a session state, display only. An accepted call that says an agent needs you brings the CODE screen on stage and holds the rotation, and stores nothing: no screen, no brightness, no setting is written. `/install?k=<token>` hands the token out inside the installer: the host, a cross-site origin and the lock are checked first, then `k` in constant time; a wrong or missing `k` gets a script that prints why and exits 1, never the token; the answer is `no-store`. Plain HTTP limit: the token travels in clear on the network, in the install command's address once and in the header of each call, so anyone sniffing the Wi-Fi can read it, and then can change what CODE shows and nothing else. Renew it if the network is not trusted. On the computer, the command stays in the shell's history and, while it runs, in the process list other accounts can read; it carries `--noproxy '*'` so that a proxy set there does not receive it. Renew it if someone else can read them. `/id` needs no token; with `?c=<nonce>` it adds an HMAC over the nonce and the panel's address, made with the token, which the hook checks before it sends the token to an address. |
| Wi-Fi setup access point (`CAROUSEL-XXXX`) | Open, by design: you must be physically next to the panel. It opens when no network is saved, when the saved network is unreachable after boot or keeps refusing the password, or when the encoder button is held at boot. It closes once the saved network actually connects. |
| Signed updates (all panels) | Firmware images are installed only if their ECDSA P-256 signature over `carousel-firmware <version> <sha256>` matches the public key in `src/updater.cpp`, and the version is newer (no downgrade). The private key is a release workflow secret, with an offline copy. Downloads use TLS with certificate checks; integrity still rests on the signature. A new image runs on trial and the bootloader rolls back if it fails. |
| Development OTA (ArduinoOTA) | Disabled unless `OTA_PASSWORD` is set in `secrets.h`; password-protected (challenge-response, not encryption). Meant for development boards. |
| MQTT | Plain TCP to the broker you set, with its user and password if any (the Panel page never sends the password back). Anyone who can publish on the broker can switch screens, change the brightness and the message, choose the image shown, and post notifications: protect the broker. MQTT never adds, replaces or deletes an image. |
| Local API (`/api/...`) | Bearer token (a 128-bit secret of its own, shown on the Panel page) or a signed-in browser's cookie; the token cannot sign a browser in. Unknown `Host` and cross-site browser requests refused. Parameters bounded in size. Known limit: the web server library reads the body of every POST except `/agent/<state>`, `/claude/<state>`, `/show`, `/brightness`, `/text` and `/wifi` (JSON and form bodies, a multipart body on any route, and the text fields of an image upload) whole into RAM before the panel checks the host, the origin, the sign-in or the token, so a device on the network or a cross-site page can send a large body and run the panel short of memory for a moment (not measured on the panel); capping these bodies is planned. See [`docs/api.md`](docs/api.md). |
| Images and uploads | An upload needs a signed-in session (Images page) or the API token. Host, cross-site, sign-in and the announced size are checked before a byte is written. A refused API upload gets its answer, then the connection closes (at most 500 ms spent dropping what is still sent); the Images page reads and drops an oversized body up to 1 MB so the browser shows the refusal, and closes above. Caps: 96 KB per image, 24 images, a reserve kept free; the file is written to flash as it arrives, never held whole in RAM (the upload's text fields are not: see the Local API row), and only the first file part is stored. A refused or interrupted upload leaves nothing. Names are cleaned to letters, digits, `-`, `_` and `.`, and never used as a path. GIFs are decoded on the panel by the firmware's own GIF decoder: bounded memory reserved only while the IMAGE screen is on, every index checked, fail-closed (a frame is drawn only when complete), fuzzed on the host with truncated and mutated files. Image names are visible to anyone who can read the MQTT broker. A deleted image stays on flash until its blocks are reused; a factory reset erases the whole image area and reads it back blank. |
| Factory reset | Hold the knob 10 s at boot. In this order: a marker is written in the image area, then the images (the `littlefs` partition), the crash dump (the `coredump` partition, a copy of RAM) and the whole NVS partition (settings, Wi-Fi password, MQTT password, API keys, sessions, the three secrets) are erased and each read back blank, and the marker is cleared last. A reset is never reported done when a step fails: the marker stays and the next start resumes it before any setting is read. Until it completes the panel is locked: NVS is closed (no setting or secret read, nothing saved; the session, API and hook secrets live in RAM only), no saved Wi-Fi, the setup access point open, RESET FAILED on the panel and its page, the image area never mounted, and `/api/text` and the image calls answer 503. A knob reset whose marker cannot be written runs every erase anyway; if one fails, the panel stays locked for that start only, and a power cycle starts normally on whatever survived. Kept on purpose, holding no user data: `app0`, `app1`, `otadata`, the bootloader and the partition table. |
| API keys (YouTube) | Stored in the panel's flash (NVS) in clear text, never sent back by the Running order page (it only says one is saved). Use a key restricted to the YouTube Data API. |
| Outbound connections | The panel itself starts these, all but NTP over HTTPS: `api.met.no` (the weather: the place's coordinates cut to 4 decimals, with a User-Agent naming the firmware version; about once an hour at the panel's own second, and also within a minute of a start, at once after a city change, and 10 min after a request that got no answer or an unreadable one), `raw.githubusercontent.com` (pieces of the city table, `data/places.bin` of the release's tag, by HTTPS range requests: while the owner types a city on the settings page, after a city is saved, and once for a place an earlier version found without a zone; nothing typed is sent, only byte ranges, though the range asked for hints at the city, since the table is sorted by name and each piece holds about 250 names; every piece is checked against SHA-256 hashes built into the firmware; a failure waits an hour, doubling to a day), the update server on GitHub (nightly), the YouTube and GitHub APIs (only with a key or user set), the router's or public NTP servers, and the MQTT broker you set. Nothing is sent about the owner beyond these. |
| HTTPS (YouTube, GitHub, updates, MET Norway, city table) | Server certificates are checked against Mozilla's root list embedded in the firmware (`firmware/certs/`, regenerated with `scripts/gen_crt_bundle.py`). |
| Coding agent hook script and installer | The hook sends only the session id, the project folder name, the state and a timestamp, never prompts or tool output. The token is read by `curl` from a file of mode 0600 in `~/.config/carousel/` (mode 0700), so it is on no command line and in no address; the agents' own files hold only the command that runs the script, never the token. It sends the token only to an address whose `/id` names the followed panel and answers the HMAC proof (without a SHA-256 tool to check it, it sends nothing); the end of a session, which must leave within 1 s, goes without a new proof only to an address proven in the last 10 minutes. It looks for the panel on the whole `/24` only on a network where it has already seen it (the address prefix and the router's hardware address): on any other network, in a café for instance, it scans nothing. It works in a per-user directory (`$TMPDIR/carousel-<uid>`, mode 0700) and does nothing if that directory is not owned by the user or is a symlink. The installer runs as the user, changes only the agents' user configuration files, removes only the exact entries it writes (and the old hook's), writes a `.carousel-backup` copy before each change, replaces a file by a move so that a failed write leaves it whole, and leaves a file that is not valid JSON untouched. It is a shell script piped into `sh` from the panel's address over plain HTTP: it is served gzip, runs nothing unless it arrived whole, and anyone who can answer in the panel's place on the network could serve a different one. Copy the command from the Panel page only. |
| Time | The clock is set by NTP (the router's time server when it names one, then public ones) and, if it comes first, by the first HTTP `Date` header the panel receives; a date before the firmware's build time is refused. This TLS configuration does not check certificate dates, so an expired certificate is not refused for its date. Signed updates do not depend on the clock: the signature and the version decide. |
| Secrets in the repository | `firmware/include/secrets.h` is git-ignored; `secrets.example.h` holds placeholders only. |
